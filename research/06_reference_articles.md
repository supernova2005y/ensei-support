## 1. 【個人開発】寝坊常習犯のための乗換案内アプリを作る ~API選定編~（Izana180、Qiita、2025-05-19）
- URL: https://qiita.com/Izana180/items/e4aa7432367371e1f134
- 見つけた経緯: 2026-10-19、交通API の選定を相談していたときにユーザーが共有
- 作っているもの: 寝過ごし・乗り遅れを防ぐ乗換案内アプリ（Flutter のアプリ＋Go のバックエンド）
- 作者の GitHub: https://github.com/Izana180 （バックエンド `NebosukeTrainRouteSearch_backend`、アプリ `onGoing_Nebosuke_trainRouteSearch`）

### 記事の要点（4つのAPIの比較）
| API | 作者の評価 | 結論 |
|---|---|---|
| NAVITIME API | 無料（月500回）。公式は法人申請のみだが RapidAPI 経由で個人契約できる。無料の割に機能が多い。上限が少ない | **採用**。ユーザーが増えて上限に届いたら収益化を考える |
| ジョルダン 乗換案内オープンAPI | 無料（月1種類3,000回・合計1万回）。非公開アプリでは使えない。審査があり、開設前は企画書が要る | 「乗換案内そのものを作る」用途は想定していないと判断して見送り |
| ODPT | 無料、申請から数十分で承認。経路検索の機能がない（ダイクストラ法などで自作が必要。全国の駅のグラフは膨大、経由駅指定も重い） | 最初は採用したが見送り |
| Google Maps Platform（Routes API） | 自由度が高い。無料の Essentials ではリアルタイムの交通情報が取れない | 見送り。収益が立てば移行を検討 |

### バックエンドの作り（GitHub の README より。コードは読んでいない）
- Go（Gin）で自前のAPIを作り、アプリはそれだけを呼ぶ。AWS EC2 で動かし、Docker を使う。外部APIは NAVITIME API と ODPT API。
- 自前のAPIは2つだけ:
  - `GET /stations`：駅の一覧（入力の候補表示用）
  - `GET /routesearch`：`from`・`to`（駅のID）、`datetime`、`isArrivalTime`（到着時刻で探すか）、`via`（経由駅）→ 区間ごとの発着駅・時刻・移動手段と、合計運賃・合計時間だけを返す
- API の仕様は SwaggerHub（OpenAPI）で公開している。

### この遠征アプリで参考にできること
1. **外部APIの返事をそのままアプリに渡さず、自前のAPIで必要な項目だけに絞って返す。** docs/開発のTODO.md のフェーズ1の「データの形を決める（Event / Transport / Stay / Spot / Plan）」と同じ考え方。外部APIを NAVITIME → 駅すぱあと などに替えても、アプリ側を直さずに済む。
2. **「到着時刻で探す」（isArrivalTime）と「経由駅」（via）を最初から入れている。** 遠征では「開演（開場）に間に合うように着く」探し方と、「品川で降りて寄り道する」探し方の両方が要る（docs/企画書.md の4章）。
3. **駅の一覧は経路検索APIとは別に持っている**（ODPT を使っているとみられる。推測）。NAVITIME の無料枠（月500回）を、駅名の候補表示のような軽い用途で使い切らない工夫として参考になる。
4. **EC2（固定IPを付けられるサーバー）で動かしている。** ジョルダンのAPIを使うなら固定IPが要るので（`research/02_apis.md` 1-2）、構成を決めるときの参考になる。
5. **無料枠で始めて、上限に届くほど使われたら有料プランや収益化を考える**、という進め方。

## 2. JavaScriptでのNAVITIME_APIの利用方法（jagaimo310、Qiita）🔶
- URL: https://qiita.com/jagaimo310/items/9e0cd34cb3ad5b7ef063
- 見つけた経緯: 2026-10-19、上の記事の関連を調べていて検索で見つけた（本文は直接は読めず、検索結果の要約から）
- 要点: **RapidAPI 経由では、バスは検索できず、電車も実際の時刻表ではなく平均の所要時間で出る。** 制限を外すには NAVITIME API のサービスページから申し込んで別のキーを取る必要がある。
- 公式の RapidAPI ページ（NAVITIME Route(totalnavi)）にも「バス情報を利用した検索は RapidAPI では提供しておりません」とあり、電車の時刻表データやバス情報が必要ならナビタイムジャパンに問い合わせるよう書かれている（検索結果の要約より）。

### この遠征アプリへの影響
- **RapidAPI の無料プランでは「終演後に間に合う最終の新幹線」は出せない見込み。** 時刻表に沿った探索は、NAVITIME の直接契約（法人向け、学術プランあり）か、駅すぱあとのスタンダードプラン（有料）が必要。ジョルダンのオープンAPIも時刻を指定できない（`research/02_apis.md`）。
- 平均の所要時間でも、**「駅から会場まで約◯分」（宿の結果の手入力の値）を置き換えるのには足りる。**

## 3. ジョルダン乗換案内オープンAPIをアプリから使う記事（個人の記事、出典URL未確認）🔶
- 見つけた経緯: 2026-10-19、ユーザーが本文を共有（タイトル・URL は未確認）
- 要点: クライアント（アプリ・ブラウザ）から直接は呼べない。審査に通ったあと、**固定の接続元IPアドレスをジョルダンに伝える**必要がある。記事では、さくらのVPS＋nginx のリバースプロキシで中継した。オープンな用途ならアプリでも可（企画の内容による）。呼び出し回数の上限があるのでキャッシュを考える必要がある。https 化も自分で行う。iOS 向けの非公式ライブラリ（NorikaeOpenAPIFramework）を作者が趣味で公開しているが、作り直す予定とのこと。
- この遠征アプリへの影響: `research/02_apis.md` 1-2、docs/開発のTODO.md のフェーズ1の「構成を決める」に反映済み。

## 付録：NAVITIME ルート検索（RapidAPI）の初回実行（2026-10-19）
> 2026-11-26 に、取った所要時間・運賃の値をこの付録から外した。NAVITIME の規約（利用規約（RapidAPI）第5条5）で、受け取ったデータは保存できないため（`docs/API規約メモ_NAVITIME.md`）。わかったこと（返事の形と、時刻の性質）だけを残す。

- 7駅→会場と、名古屋駅→会場で、計8回呼んだ。
- **所要時間は徒歩込みで返る。** 手で入れていた目安は乗車時間だけで、駅と会場の両側の徒歩を含んでいなかったので、短く見積もっていた。→ 人が確かめるときも、徒歩込みで測る。
- **運賃は種類ごとの番号で返る。** 名前はレスポンスになかったので金額から推定：`unit_0` 乗車券（きっぷ）、`unit_48` IC、`unit_1` 特急券（自由席）、`unit_2` 特急券（指定席）、`unit_3` 特急券（グリーン）、`unit_128_train`・`unit_130_train`・`unit_133_train` 定期券（1・3・6か月とみられる）。**新幹線の自由席・指定席・グリーンが分かれて返る**ことを確認。
- **時刻表どおりではなく、平均の所要時間であることを確認した。** 出発時刻を指定すると、候補がすべてその時刻ちょうどに出発する形で返り、到着は出発時刻に所要時間を足しただけの値だった。→ **終演後に間に合う最終便の判断には使えない。** 使えるのは所要時間の目安と運賃。
- 2026-11-26 にもう一度確かめた：会場→名古屋を終演後の時刻で検索すると、品川で乗るのぞみの発車時刻が、実際のダイヤ（ユーザーが乗換検索で確認）と合わなかった。乗り換えの待ちを平均で見込んでいるとみられる。
