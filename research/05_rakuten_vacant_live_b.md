## 気づいたこと・次にやること
- **件数で4等分する分け方は粗い。** 「最安」の中に1万円台と3万円台が同居する。最安値からの倍率や料金の切れ目で分けるなど、分け方を見直す。
- **半径3.0kmで検索したのに、手元の距離計算で3.5kmほどの施設がある。** 座標の基準（楽天側の施設座標、中心座標のずれ）を確認する。
- **試作でリーズナブルの例にしたホテルA が出てこない。** 満室なのか楽天に載っていないのかを、施設検索APIで切り分ける。
- **高騰の大きさを測る：** 同じ条件で前日・翌日・公演のない週末（例：翌週の日曜）を取り、公演日の上乗せ分を出す。
- 最寄り駅が空で返ってくるホテルがあった。最寄り駅がない施設の扱いを決める。

| 宿泊日 | 状況 | 空室ありの施設 | 料金の中央値 | 公演のない翌週の日曜と比べた倍率（同じ施設どうし、中央値） |
|---|---|---|---|---|
| 前日（土） | 同じ会場で公演・前泊 | 10件 | 約55,700円 | **1.8倍**（1.35〜3.6倍） |
| 公演日（日） | 公演当日・翌日祝日 | 18件 | 約44,100円 | **1.9倍**（1.3〜3.6倍） |
| 翌日（月・祝） | 後泊 | 27件 | 約19,600円 | **1.0倍**（0.5〜2.0倍） |
| 翌週の日曜 | 公演なし（基準） | 30件以上 | 約16,900円 | — |

- **公演のある夜（前日・公演日）は、同じ施設でも約2倍、最大3.6倍になる。** 例：会場近くのあるホテルが 3千円台（翌週の日曜）→ 1万3千円台（前日・公演日）
- **会場の近くから満室になる。** 翌週の日曜には空いていた会場から1km圏内（0.2〜0.8km）のホテル4件が、公演日には空室なし。
- **後泊（翌日）はほぼ通常の料金に戻る。** 上の例と同じホテルが、公演の夜の1万3千円台から4千円台に戻る（約3分の1）。「公演の夜は避けて、前後にずらす」提案に意味がある。
- 注意：翌週の日曜は30件（1ページの上限）ちょうどなので、ほかにも空室のある施設がある可能性がある（`--pages 2` で確認できる）。料金は10/19時点のもので、公演が近づくと変わる。

### プロダクトへの示唆
- 公演の夜の値上がりは利用者には倍率で見せない（下の「表示とグレード分けの方針」）。後泊がほぼ通常の料金で泊まれることは、泊まる選択を後押しする材料になる。
- 公演日と別の日を取り比べる処理は、裏側の分析（早めの予約を勧めるタイミングなど）に使う。

## 表示とグレード分けの方針（2026-10-19決定）
- **泊まる方向に誘導する**（予約は楽天アフィリエイト経由で収益になる）。「早めの予約」「後泊なら◯円」で泊まる選択を後押しする。
- **「普段の◯倍」は利用者に見せない。** 泊まりたくない気持ちにさせるため。信頼は、予約ページと一致する本当の値段を出すこと・嘘であおらないことで保つ。倍率は裏側（早めの予約を勧める通知のタイミングなど）で使う。
- **空室のない施設の数は見せる**（事実で、早めの予約の理由になる）。施設検索API（SimpleHotelSearch）で半径内の楽天掲載施設をすべて取り、空室検索の結果と突き合わせて数える。「楽天で空室なし」であって、ほかの予約サイトでは空いている可能性はある。
- **グレードは施設の最安料金の目安（hotelMinCharge、日付に関係ない値）で決める。** 1週間後など別の日を「普段」とする案は、会場の近くは毎週のように公演があるので不採用。
- 試しに翌週の日曜の料金を最安料金の目安の代わりに当てはめると、ホテルの格に沿った分け方になった。hotelMinCharge が実際にどんな値で返るかは未確認。

## 施設検索API＋最安料金の目安での実行結果（2026-10-19）
- 施設検索API（SimpleHotelSearch）は通った。半径3km内の楽天掲載は31件、公演日に空室ありは18件・空室なし13件。
- **会場から1km以内は6件中4件が空室なし**。
- **最安料金の目安（hotelMinCharge）はグレード分けには使いにくい。** 境目が 5,750円 / 7,700円 / 11,794円と、どの日の実際の料金よりかなり低い（閑散期や複数人1室の1人あたりの料金などが入っているとみられる）。翌週の日曜の料金で分けた場合と比べると18件中9件のグレードが1段ずれ、ホテルの格とも合わない。グレード内で値段が逆転して見える（「ちょっとリッチ」に87,832円、「奮発」に35,080円）。
- → グレードの意味（払う額で分けるか、ホテルの格で分けるか）を決め直す必要がある。

## グレード分けの決定と探す範囲の拡大（2026-10-19）
- **グレードは宿泊日に実際に払う料金で分ける（A案に決定）。** 「奮発」「ちょっとリッチ」はお金の使い方の言葉で、選んだグレードと払う額が必ず一致する。宿の良し悪しは評価（★）と会場へのアクセスを横に出して補う。
  - 境目は料金の切れ目で決める（対数をとった料金を、グループ内のばらつきが最小になるよう4つに分ける）。公演日の料金を当てはめると 最安 13,200〜 / リーズナブル 25,200円〜 / ちょっとリッチ 46,500円〜 / 奮発 81,900円〜 になり、件数で4等分したときのように13,200円と31,680円が同じグループに入ることはなくなった。
  - ホテルの格で分ける案（B案）は、格を測る良い物差しがない（最安料金の目安は粗すぎる）ので見送り。
- **空室のない施設は 1km・2km・3km の距離ごとに数える**（1kmだけでは狭いため）。
- **会場へ行きやすい駅の周りの宿も探す。** 公演ごとの設定ファイル（`events/live-b.json`）に、駅の座標と会場までの乗車時間を書き、駅の半径0.6kmで空室検索する。乗車時間は手で入れた目安で未確認。NAVITIME API をつないだら置き換える。

## 駅の周りまで広げた結果と、表示の調整（2026-10-19）
- 会場の周り＋行きやすい7駅の周りで、公演日に空室のある施設は93件（会場の周りだけだと18件）。大井町駅から200mほどの簡易ホテルが8千円台（会場までりんかい線で約10分）など、公演の夜でも手頃に泊まれる宿がある → 泊まる方向への誘導の材料になる。
- 会場の周りで楽天に空室がない施設：1km以内 6件中4件 / 2km以内 11件中5件 / 3km以内 20件中6件。
- 調整したこと：
  - **民泊・アパート型は除く**（名前の「民泊」「＾」「Apart」「ハイツ」などで判定。93件中8件）。部屋まるごとの料金で比べにくく、評価もないことが多いため。
  - **各グレードに最低でも全体の15%を入れる。** 切れ目だけだと 最安8件・リーズナブル44件 のように偏ったため。調整後は 最安12件（8,680〜28,260円）/ リーズナブル38件 / ちょっとリッチ23件 / 奮発9件。
  - ~~「奮発」は★4.0以上・評価10件以上に絞る~~ → 下の「奮発の条件の見直し」で変更。
  - `--grade` で選んだグレードだけを表示する。全部の宿を取ってから境目を決めるので、API を呼ぶ回数は変わらない。
  - 人数が2人以上なら1人あたりの料金も出す。最初の選択画面（README 3章の①）に「遠征の人数」を追加。

### 奮発の条件の見直し（2026-10-19）
- ★4.0以上に絞る条件では、汐留の最高級ラグジュアリーホテル（★3.5台）が外れてしまった。**楽天の評価は「値段のわりにどうか」も入るので、高級ホテルほど低めに出る。** 評価の高さは「素敵なホテルか」の物差しにならない。
- 新しい条件：**評価の高さでは絞らず、明らかに評判が悪い宿（★3.0未満・評価10件以上）だけを外す。** 評価がまだない新しいホテルは外さず「評価がまだない」と出す。並びは料金順。
- **「ちょっとリッチ」の値段で評価がとても高い宿（★4.7以上・評価30件以上）は、「奮発」の下に「評価が高いのに手頃」として添える**（案2）。公演日では3件（★4.8以上・6〜8万円台）。
- 本物のAPIで実行して確認済み（2026-10-19）：「奮発」12件に、上で外れてしまった汐留の高級ホテルが入り、「評価が高いのに手頃」に上の3件が出た。
