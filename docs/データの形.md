# データの形（フェーズ1）

1つの公演について、JSON が2つある。

| ファイル | 中身 | 誰が読むか |
|---|---|---|
| `events/<名前>.json` | **公演の設定**：会場（座標・開場・開演・終演の目安）、宿泊日、会場へ行きやすい駅と所要時間、出発地、帰りの乗車駅 | Next.js アプリ（`src/lib/events.ts` の `EventConfig`）と `scripts/` の確認用スクリプト |
| `data/<名前>.json` | **自分で決めた候補**：泊まり方・交通の候補・ご飯の目安・駅・立ち寄り先（店名・公演名は実名）。**宿（楽天）は入れない**（2026-11-24） | まだ誰も読んでいない（試作の HTML の値を書き出したもの） |

**元になるのは `events/` の方**。会場や時刻は `events/` にだけ書き、`data/` を書き出すときにそこから写す（値を二重に持たない）。
`data/` には、**API から取った中身（楽天の宿・空室、ホットペッパー・Google の店名・住所・営業時間）を入れない**。保存するのは、自分で決めた候補だけ。API は表示のたびに取りに行き、回数の上限で止める（`CLAUDE.md` の「API で取ったデータの扱い」）。

## events/（公演の設定）

項目名は `src/lib/events.ts` の型に合わせて camelCase。

| 項目 | 例 | メモ |
|---|---|---|
| `name`・`artist`・`tourName`・`date` | 公演B | `date` がなければ `checkin` を公演日とみなす |
| `venue`（`name`・`lat`・`lng`・`open`・`start`・`endEstimate`） | SGC HALL ARIAKE・16:00・17:00・19:30 | 終演は公式発表がないので目安（`endNote` に根拠） |
| `checkin`・`checkout` | 2026-12-13・2026-12-14 | 楽天の空室検索に使う |
| `stations`（`name`・座標・`minutes`・`line`） | 豊洲・（未確認なら null） | 会場へ行きやすい駅。この周りの宿も探す。時間と路線は人が乗換検索で確かめた値（NAVITIME の結果は規約で保存できない） |
| `origin` | 名古屋駅 | 出発地 |
| `homeward`（`to`・`exitMinutes`・`boarding`） | 名古屋・20分・東京／品川 | 終演後の最終便の判定（`data/last-trains.json` と合わせて使う）。`boarding` の `minutes` も人が確かめた値。未確認なら null で、その駅の便は「判定できない」になる |

## data/（試作の固定値）

```
公演（event）
 ├─ 泊まり方（patterns）     後泊／前泊／日帰り
 ├─ 交通（transport）        泊まり方ごとの、行きと帰りの候補
 ├─ ご飯（food_grades）      1日あたりの目安
 ├─ 駅（stations）           乗り降りする駅と、その周りを探す起点
 └─ 立ち寄り先（spots）      ジャンルつき。どの駅の周りか（hub）を持つ
            ↓ ユーザーが選ぶ
      旅のしおり（plan）      日ごとの旅程と総額（まだ作っていない）
```

### 共通の決まり

- **値段は「目安・下限・上限」の3つで持つ**（`price: {yen, min, max, estimated}`）。幅がないものは3つとも同じ値。`estimated: true` は公式の値が見つからず推定したもの
- 値段の単位は円（税込み）。時刻は `HH:MM`（日本時間）の文字列、日付は `YYYY-MM-DD`
- `needs_check: true` は営業時間や営業状態をまだ確かめていないもの。しおりに「要確認」と出す
- `id` は1つの JSON の中で重ならない英小文字

### それぞれの項目

#### event（公演）

| 項目 | 例 | フェーズ2で取る先 |
|---|---|---|
| `artist`・`date` | 公演B・2026-12-13 | `events/` から写す（もとはユーザーの入力） |
| `venue`（名前・緯度経度） | SGC HALL ARIAKE | `events/` から写す（公演情報のデータ源は未定。企画書の6章の課題） |
| `doors`・`start`・`end_estimate` | 16:00・17:00・19:30 | `events/` の `open`・`start`・`endEstimate` から写す |
| `notes` | 翌日が祝日、など | 祝日の判定と、同じ会場の前後日の公演 |

#### transport（交通）

| 項目 | 意味 | フェーズ2で取る先 |
|---|---|---|
| `direction` | `go`（行き）／`back`（帰り） | — |
| `pattern` | どの泊まり方のときの候補か | — |
| `depart`・`arrive`・`duration` | 出発・到着・所要時間 | NAVITIME API |
| `price` | 運賃（バスは幅つき） | 新幹線は NAVITIME、高速バスは Web 検索（API なし） |

#### 宿（stays）：data/ から外した

楽天の宿の名前・料金は保存しない方針のため、`data/` の `stays` は削除した（2026-11-24）。宿は、表示のたびに楽天の空室検索（`/api/stays`）で取る。`tools/extract_prototype_data.mjs` も、`stays` を書き出さないように直した。

#### stations（駅）と spots（立ち寄り先）

- `stations` は地図に出す駅。`spots.hub` はここの `id` を指す
- `spots.hub` は「どの駅の周りで探したか」のまとまり（`tokyo`＝東京駅・丸の内、`ariake`＝有明・豊洲、`far`＝少し足をのばす先）。画面2の見出しになる
- `spots.genres` は `genres` のどれか
- `hours`・`availability`・`needs_check` は、フェーズ2で Google Places API（店）と Web 検索（展覧会・イベント）から入れる

## data/ の作り直し方

```bash
node tools/extract_prototype_data.mjs prototype/plan-flow-live-b.html events/live-b.json data/live-b.json
```

書き出すときに、値段の下限 ≦ 目安 ≦ 上限、交通の値段が範囲に入っているか、立ち寄り先のジャンルが `genres` にあるか、を確かめる。合わなければ止まる。
